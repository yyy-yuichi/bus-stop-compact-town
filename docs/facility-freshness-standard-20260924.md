# 施設データ鮮度・確認基準（2026-09-24 初版）

## 目的と適用範囲

本基準は、バス停と暮らしマップの施設データについて、現在も実在・営業・指定されているか、閉店・廃止・休止・移転・改称・新設がないかを、根拠を残しながら確認するための運用基準である。初期対象はアプリ内の商業施設 5,065 件と公共・生活関連施設 2,699 件、計 7,764 件。件数は 2026-09-20 の Drive 側 freshness inventory に基づく。

確認対象を「地点」「事業所／サービス」「地図上の掲載レコード」に分ける。同じ住所に複数のサービスがあっても、サービスの廃止を建物や他サービスの閉鎖とみなさない。事業所名が似ていても、住所・運営者・サービス種別・識別子を確かめず同一地点に統合しない。

## 状態の定義

| 状態 | 意味・扱い |
| --- | --- |
| 未確認（unverified） | 現在の稼働・存在を裏付ける確認がない。データ日付だけで状態を推定しない。 |
| 再確認期限超過（needs_recheck） | 設定した確認間隔を超過。閉店扱いにはせず、優先度を上げる。 |
| 候補（candidate） | 変更・同一性を示唆する情報があるが、公式一次資料との対応が未確定。 |
| 稼働確認（verified_operating） | 確認日に有効な一次資料または施設自身の現行情報で、対象の地点／サービスの現状を確認できた。確認範囲も記録する。 |
| 廃止確認（closed_confirmed） | 施設自身または管轄機関の一次資料が、対象の地点またはサービスの終了を明示している。サービス廃止と建物閉鎖は別々に記録する。 |
| 予定変更（scheduled_change） | 閉店・移転・改称・開設等が発表済みだが、適用日が将来である。発表日と実施予定日を分けて記録し、実施日前に閉店・移転済みとして扱わない。 |
| 一時休止（temporary_suspension） | 休止期間を明示する一次資料がある。期間終了後も自動で稼働扱いにせず、再確認する。 |
| 移転（moved） | 同一の事業所・運営主体等が移転した一次資料が確認できた。旧地点の履歴と新地点のレコードを結び付ける。 |
| 改称（renamed） | 同一対象の名称変更を一次資料で確認できた。旧名称を履歴として保持する。 |
| 新設候補（new_location_candidate） | 新設情報と既存レコードの同一性・近接性を調べる必要がある。候補だけで自動追加・統合しない。 |
| 根拠競合（conflict） | 現行資料間で矛盾する、または対象の同一性を確定できない。人による保留・追加確認へ回す。 |

状態には必ず確認日と根拠をひも付ける。期限超過や資料不在は「閉店確認」への遷移理由にしない。

## 根拠の優先順位と判定ルール

1. 規制・指定事業所は、管轄官公庁の現行台帳と、指定・廃止・休止・変更の公式告知を最優先する。対象の行政上の指定状態と、建物・店舗の物理的な現状は別の問いとして扱う。
2. 施設・運営者が発信した一次資料を確認する。公式サイト、ニュースリリース、公式SNS（Instagram等）の投稿、施設が自ら管理するGoogleビジネスプロフィールの投稿・営業時間変更は、発信元と対象店舗を確認できた場合に一次情報として扱える。公式LINEは配信内容が確認可能な場合に限り、同様に扱う。
3. Google Mapsの表示は発信主体を区別する。施設オーナーによる更新と確認できる情報は運営者情報として扱う。一方、利用者の編集提案・口コミ・写真、Googleが他情報を基に反映した変更など、発信元が特定できない表示は変化の手掛かりに留め、表示だけで閉店・開店・所在地を確定しない。
4. ニュース記事、検索結果、OSM、第三者ディレクトリ、地域SNS、利用者投稿は、閉店・開店・移転・改称などの候補発見と優先順位付けに使う。記事が公式発表を報じている場合は記事の要約ではなく引用元の原ページを開いて照合する。一次資料が見つからない場合は候補または根拠競合に留める。
5. アカウントが「公式」かは、認証バッジだけで判断しない。施設公式サイト、運営者の企業サイト、他の公式アカウント等から相互リンクされているか、運営者名・対象店舗・住所が整合するかを記録する。チェーン本部の公式発信でも、対象の支店・店舗への適用範囲を確認する。
6. 一次資料の台帳から行が消えたことだけでは閉鎖としない。改称、移転、対象範囲、掲載遅延、データ移行の可能性を調べる。
7. 公式資料にない新規施設は、運営者の公式発表等の一次資料を探す。裏付けが取れるまでは候補のままにする。
8. 一つの事業所に複数サービスがある場合、廃止資料のサービス種別・事業所番号・運営者・住所をアプリ側の対象と照合する。サービスの廃止を全施設の削除に拡張しない。

## ニュース・SNS・地図サービスによる変化検知

- 公式店舗一覧だけでなく、運営会社・施設運営者のニュース／お知らせ、公開されているInstagram等の投稿、確認可能な公式LINE配信、Googleビジネスプロフィールの投稿・営業時間・状態を調べる。施設の種類に応じて、自治体・公的機関の現行台帳も併用する。
- 検索語は「施設名 閉店／営業終了／移転／開店／オープン／新規開設／休業／リニューアル」。旧称、運営会社名、支店名、市町名、住所も組み合わせる。記事・投稿の発信日、告知日、対象日、実施日、取得日を別々に記録する。
- Google Mapsではプロフィールの閉店表示だけを根拠にしない。可能なら投稿者・変更元（オーナー、利用者、Google等）を特定し、公式の店舗ページや運営者告知と照合する。来店者の写真・口コミは「最近そこに営業実態がありそう」という追加調査のきっかけにはなるが、古い写真、隣接店、施設内テナントの取り違えを排除するまで確定根拠にしない。
- Instagram等は投稿・リールの店舗名、住所、告知日、実施予定日、アカウントとの紐づきを保存する。ストーリーズ等、後から見えなくなる情報は、閲覧日時と取得できた範囲を記録し、保存が許可された範囲で証跡を残す。非公開アカウント、ログイン限定コンテンツ、個人宛ての非公開メッセージは、閲覧・収集できる前提にしない。
- LINE公式アカウントの一斉配信は友だち向けの情報で、常に一般検索から読めるとは限らない。一般公開の投稿または正当に閲覧できる配信、ユーザーから提供された記録のみを根拠にする。LINE VOOMはLINE公式案内で2026-09-30の提供終了が告知されているため、継続的な監視先として前提化せず、作業時点の公開機能を確認する。
- 将来の閉店・開店・移転予定は `scheduled_change` として残す。告知時点では現在の状態を維持し、予定日後に実際の営業状態を再確認する。開店予定だけでは稼働確認にせず、閉店予定だけでは閉店確認にしない。
- 報道・利用者投稿・地図の利用者編集しか見つからない場合は候補として保留し、公式一次資料、対象施設への直接確認、または人による追加調査へ回す。複数の二次情報が一致しても、それだけで公式確定へ格上げしない。
- 変化候補がどのアプリレコードかは、店舗単位の名称・旧称・運営者・住所・元ID・座標を照合して決める。ニュースやSNSに記載のない点座標・建物範囲・入口は推測しない。

## 多数施設をタイムリーに確認する運用

全件の全チャネルを毎回手で検索するのではなく、発見と確定を分けた候補キューで回す。

1. コードで名称・旧称・運営者・住所・元IDを正規化し、同じ店舗への検索候補をまとめる。RSS、公式更新一覧、オープンデータの差分等が提供される情報源は一括取得し、そうでないSNSやGoogleプロフィールは公開ページの検索・個別確認など、利用可能な方法を情報源ごとに記録する。
2. ニュース、公式投稿、Google Mapsの状態変更、自治体告知、利用者情報などから変化候補を集め、対象店舗候補・イベント種別・発見日時・発信主体を付けて重複を除く。全施設の監視を装わず、未確認の情報源・監視できないアカウントも明示する。
3. コードでID・住所・近接・日付を処理し、Jevは候補の同一性や調査優先度の事前振り分けに使う。Jevの出力、検索順位、情報の不在は事実の証明にしない。
4. 高リスク候補だけを一次資料確認へ送り、GPT-6 Proは検索・同一性が曖昧な少数例の調査補助とする。Codexが原ページ、対象店舗、元IDの対応を独立確認し、人が更新内容を承認した後に差分反映する。
5. 試行ごとに「確認施設数」だけでなく、監視できた情報源の範囲、候補件数、一次資料まで確認できた件数、正候補・誤検知・保留、候補発見から反映までの時間、情報源別の所要時間を測る。実測で有効な情報源と確認間隔を選び、カバーできない施設を「変更なし」と扱わない。

各観測には、少なくとも以下を保存する。

- app record ID と元データの source ID（保持・不変）
- 地点／事業所／サービスのどれを確認したか
- 情報源種別（官公庁、運営者公式サイト、公式SNS／公式LINE、Google Mapsのオーナー情報・利用者情報・Google反映、報道、その他）と発信主体・アカウントの公式性確認方法
- 確認状態、確認日（checked_at）、根拠資料の対象日（source_as_of）、取得日（retrieved_at）
- 発表日（announced_at）と変更の実施日・予定日（effective_at）。該当資料に記載がない場合は推測せず空欄とする。
- 発行元・資料名・直接URL、確認した記載内容
- 照合に使った識別子、名称、住所、運営者、サービス種別、および照合方法
- 自動候補、Jevの振り分け結果（使った場合）、人の採否とその理由
- 投稿が削除・更新・期限切れになる場合は、確認時に保存できた公開範囲、投稿URLまたは証跡参照、取得日時。非公開メッセージの全文や第三者の個人情報は転記しない。

変更は観測履歴へ追記し、元の値を上書きで失わない。アプリ反映は一次資料と対象IDが結び付き、人が変更内容を確認した後に行う。

## Jev・GPT・決定的処理の使い分け

- コードで行うこと：件数、日付計算、文字列正規化、住所・座標距離、行政番号等の完全一致、候補の重複除去、台帳差分、ファイル形式検証。
- Jevで行うこと：コードで絞り込んだ候補について、名称・運営者・住所・サービスの意味的な関係を「同一候補／別候補／保留」等へ分類し、調査順序を提案する。入力に根拠文を含めても、Jevの出力自体は事実の証明にしない。
- 通常のGPT-6 Pro調査へ回すもの：一次資料を検索しても対象を特定できない高リスク候補、資料間の競合、曖昧な移転・改称。調査対象を少数に絞り、主張は独立に一次資料で検証する。
- 人が最終確認すること：閉店・移転・改称・新規追加の確定、誤統合の解消、アプリデータへの反映。

Jevの有用性は速度だけでなく、「機械的に候補を縮約できた数」「保留に回せた曖昧例」「人が一次資料を読むのに要した時間」「誤った同一視・見落とし」で評価する。低い信頼度や高リスク判定は自動反映しない。モデル評価時間・トークン数は実行条件付きの参考値であり、外部検索時間や全業務時間とは区別する。

## 初期の再確認間隔（仮）

| データ群 | 定期確認 |
| --- | --- |
| 商業・飲食・消費者向け施設（OSM由来を含む） | まず四半期ごとに高リスク・古い・変更兆候のある候補を再検索。全件を毎回手作業確認する前提にはしない。 |
| 介護等の指定事業所 | 月次の公式な新規指定・廃止・休止差分を確認し、半年ごとに現行台帳と全件照合。 |
| 学校・公共施設・公園等 | 公的データの更新周期と公式の統廃合・閉鎖情報を年次確認。更新周期が不明ならそれ自体を記録する。 |

この間隔は初期運用値であり、試行で見えた変更率・誤判定・確認負荷に応じて調整する。取得元の掲載日が古い場合は優先順位を上げるが、それを現況の否定と混同しない。

## 2026-09-24 の検証可能な初期値

Drive 側の 2026-09-20 inventory では 7,764 件中、7,742 件は稼働状況が未確認。名称・住所等の照合記録がある 22 件も、稼働確認とは記録されていない。2,661 件は元ソース日付が1年超前、2,470 件は2年超前、4,950 件は公式URLなし。これらは確認優先度の指標であり、閉店件数ではない。

山口県の介護事業所の月次資料を用いた初回の小規模試行、Jev候補振り分け、未変更の照合メモは data-sources/facility-freshness-baseline-20260924/pilot.md に記録する。
