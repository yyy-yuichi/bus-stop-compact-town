# 施設データ鮮度・確認基準（2026-09-24 初版）

## 目的と適用範囲

本基準は、バス停と暮らしマップの施設データについて、現在も実在・営業・指定されているか、閉店・廃止・休止・移転・改称・新設がないかを、根拠を残しながら確認するための運用基準である。初期対象はアプリ内の商業施設 5,065 件と公共・生活関連施設 2,699 件、計 7,764 件。件数は 2026-09-20 の Drive 側 freshness inventory に基づく。

確認対象を「地点」「事業所／サービス」「地図上の掲載レコード」に分ける。同じ住所に複数のサービスがあっても、サービスの廃止を建物や他サービスの閉鎖とみなさない。事業所名が似ていても、住所・運営者・サービス種別・識別子を確かめず同一地点に統合しない。

## 状態の定義

| 状態 | 意味・扱い |
| --- | --- |
| 未確認（unverified） | 現在の稼働・存在を裏付ける確認がない。データ日付だけで状態を推定しない。 |
| 再確認期限超過（needs_recheck） | 設定した確認間隔を超過。閉店扱いにはせず、優先度を上げる。 |
| 候補（candidate） | 変更・同一性を示唆する情報があるが、公式一次資料との対応が未確定。 |
| 稼働確認（verified_operating） | 確認日に有効な一次資料または施設自身の現行情報で、対象の地点／サービスの現状を確認できた。確認範囲も記録する。 |
| 廃止確認（closed_confirmed） | 施設自身または管轄機関の一次資料が、対象の地点またはサービスの終了を明示している。サービス廃止と建物閉鎖は別々に記録する。 |
| 予定変更（scheduled_change） | 閉店・移転・改称・開設等が発表済みだが、適用日が将来である。発表日と実施予定日を分けて記録し、実施日前に閉店・移転済みとして扱わない。 |
| 一時休止（temporary_suspension） | 休止期間を明示する一次資料がある。期間終了後も自動で稼働扱いにせず、再確認する。 |
| 移転（moved） | 同一の事業所・運営主体等が移転した一次資料が確認できた。旧地点の履歴と新地点のレコードを結び付ける。 |
| 改称（renamed） | 同一対象の名称変更を一次資料で確認できた。旧名称を履歴として保持する。 |
| 新設候補（new_location_candidate） | 新設情報と既存レコードの同一性・近接性を調べる必要がある。候補だけで自動追加・統合しない。 |
| 根拠競合（conflict） | 現行資料間で矛盾する、または対象の同一性を確定できない。人による保留・追加確認へ回す。 |

状態には必ず確認日と根拠をひも付ける。期限超過や資料不在は「閉店確認」への遷移理由にしない。

## 根拠の優先順位と判定ルール

1. 規制・指定事業所は、管轄官公庁の現行台帳と、指定・廃止・休止・変更の公式告知を最優先する。対象の行政上の指定状態と、建物・店舗の物理的な現状は別の問いとして扱う。
2. 施設自身の公式サイト・公式発表、運営者の告知、自治体等の現行オープンデータを次に確認する。発表日・実施予定日・対象日・取得日を区別する。
3. ニュース記事、検索結果、Google Maps、OSM、第三者ディレクトリは、閉店・開店・移転・改称などの変化を見つける手掛かりとして使う。ニュース記事だけで確定せず、運営者・管轄機関の原ページや公式発表を開いて照合する。公式一次資料を見つけられなければ候補または根拠競合に留める。
4. 一次資料の台帳から行が消えたことだけでは閉鎖としない。改称、移転、対象範囲、掲載遅延、データ移行の可能性を調べる。
5. 公式資料にない新規施設は、運営者の公式発表等の一次資料を探す。裏付けが取れるまでは候補のままにする。
6. 一つの事業所に複数サービスがある場合、廃止資料のサービス種別・事業所番号・運営者・住所をアプリ側の対象と照合する。サービスの廃止を全施設の削除に拡張しない。

## ニュース・告知による変化検知

- 商業施設は、現行の公式店舗一覧だけでなく、運営会社・施設運営者のニュース／お知らせ欄も検索する。自治体や公的機関の指定・廃止資料も、施設の種類に応じて併用する。
- 検索語の例は「施設名 閉店」「施設名 営業終了」「施設名 移転」「施設名 開店」「施設名 リニューアル」。旧称・運営会社名・市町名も組み合わせ、記事の公開日と変更の実施日を別々に記録する。
- 将来の閉店予定は `scheduled_change` として残す。告知時点で営業中なら、現在の稼働状態は維持し、実施日後に営業終了を再確認してから `closed_confirmed` へ移す。
- 報道記事は変化の発見・優先順位付けに使えるが、対象の施設・店舗がどの地図レコードかは別途住所、運営者、元ID、位置情報で照合する。記事に書かれていない点座標・建物範囲・入口を推測しない。

各観測には、少なくとも以下を保存する。

- app record ID と元データの source ID（保持・不変）
- 地点／事業所／サービスのどれを確認したか
- 確認状態、確認日（checked_at）、根拠資料の対象日（source_as_of）、取得日（retrieved_at）
- 発表日（announced_at）と変更の実施日・予定日（effective_at）。該当資料に記載がない場合は推測せず空欄とする。
- 発行元・資料名・直接URL、確認した記載内容
- 照合に使った識別子、名称、住所、運営者、サービス種別、および照合方法
- 自動候補、Jevの振り分け結果（使った場合）、人の採否とその理由

変更は観測履歴へ追記し、元の値を上書きで失わない。アプリ反映は一次資料と対象IDが結び付き、人が変更内容を確認した後に行う。

## Jev・GPT・決定的処理の使い分け

- コードで行うこと：件数、日付計算、文字列正規化、住所・座標距離、行政番号等の完全一致、候補の重複除去、台帳差分、ファイル形式検証。
- Jevで行うこと：コードで絞り込んだ候補について、名称・運営者・住所・サービスの意味的な関係を「同一候補／別候補／保留」等へ分類し、調査順序を提案する。入力に根拠文を含めても、Jevの出力自体は事実の証明にしない。
- 通常のGPT-6 Pro調査へ回すもの：一次資料を検索しても対象を特定できない高リスク候補、資料間の競合、曖昧な移転・改称。調査対象を少数に絞り、主張は独立に一次資料で検証する。
- 人が最終確認すること：閉店・移転・改称・新規追加の確定、誤統合の解消、アプリデータへの反映。

Jevの有用性は速度だけでなく、「機械的に候補を縮約できた数」「保留に回せた曖昧例」「人が一次資料を読むのに要した時間」「誤った同一視・見落とし」で評価する。低い信頼度や高リスク判定は自動反映しない。モデル評価時間・トークン数は実行条件付きの参考値であり、外部検索時間や全業務時間とは区別する。

## 初期の再確認間隔（仮）

| データ群 | 定期確認 |
| --- | --- |
| 商業・飲食・消費者向け施設（OSM由来を含む） | まず四半期ごとに高リスク・古い・変更兆候のある候補を再検索。全件を毎回手作業確認する前提にはしない。 |
| 介護等の指定事業所 | 月次の公式な新規指定・廃止・休止差分を確認し、半年ごとに現行台帳と全件照合。 |
| 学校・公共施設・公園等 | 公的データの更新周期と公式の統廃合・閉鎖情報を年次確認。更新周期が不明ならそれ自体を記録する。 |

この間隔は初期運用値であり、試行で見えた変更率・誤判定・確認負荷に応じて調整する。取得元の掲載日が古い場合は優先順位を上げるが、それを現況の否定と混同しない。

## 2026-09-24 の検証可能な初期値

Drive 側の 2026-09-20 inventory では 7,764 件中、7,742 件は稼働状況が未確認。名称・住所等の照合記録がある 22 件も、稼働確認とは記録されていない。2,661 件は元ソース日付が1年超前、2,470 件は2年超前、4,950 件は公式URLなし。これらは確認優先度の指標であり、閉店件数ではない。

山口県の介護事業所の月次資料を用いた初回の小規模試行、Jev候補振り分け、未変更の照合メモは data-sources/facility-freshness-baseline-20260924/pilot.md に記録する。
