検証日：2026-09-14。対象：このPCにインストール済みの `C:/Users/user/.codex/skills/project-continuity/` の5ファイル。ユーザーの「そのまま使ってよいか検証して」を受け、実案件へ導入する前に確認した。

## 結論

今回のバス停と暮らしマップには、補助CLIと `.codex/continuity/` のJSON管理方式を導入しない。既存のMarkdown記録とgoal-to-doneで進める。根拠・未完了作業・承認の範囲を残す考え方は有用だが、スキルを呼び出したことや検証コマンドの成功を、事実確認・正式保存・完了の証拠にしない。

スキルの説明文は、既存Markdownの維持、承認の持ち越し、Driveの読み戻し、積算保護、削除の承認、不要な全体複製の抑制を明記しており、これらの方針は本案件のルールと整合する。ただし説明文と補助スクリプトを一括して無条件に採用できる、という結論ではない。

## 実際に確認した問題・限界

1. **承認の扱いに文言の不一致がある。** `scripts/continuity.py` の初期状態には `Perform external mutations without authorization from the current request.` が入る。説明文は以前の明示承認を持ち越すとしており、本案件でもセッション内の承認は継続する。「現在の依頼」にだけ限定して再承認を求める運用は採用しない。逆に、記録に承認が書かれているだけで別対象への公開・送信を許可したことにもしない。

2. **CHECKPOINT_READYは、外部保存や内容の正しさの証明ではない。** 隔離した架空案件で、実在しない `https://example.invalid/does-not-exist` を証拠URIに登録し、架空の完了項目と自己申告レビューを記録すると、validateはexit 0・CHECKPOINT_READYになることを再現した。これは仕様に明記された限界で、想定外の通信障害や外部情報漏洩を発見したという意味ではない。実際の案件への虚偽の完了記録は作成していない。

3. **Gitの指紋は、すべての未追跡ファイルの内容を検査しない。** 未追跡ファイルの内容を同じ長さに変え、更新日時を保った場合、Gitの指紋は変わらなかった。仕様どおりサイズ・日時による追跡であり、重要な証拠は別途明示的に内容ハッシュを検査する必要がある。無条件の「ファイルは全部一致した」という扱いはできない。

4. **このWindows環境では文字コードの条件が必要。** 初回、親Pythonだけを `-X utf8` で起動すると、子プロセスの日本語パスを含む出力の読み取りでUnicodeDecodeErrorが発生した。付属10テストはその状態でもOKを報告した。テスト用実行環境でUTF-8設定を子プロセスへ継承した再実行では、10テストと追加検証が例外なく終了した。インストール済みスクリプトは変更していない。

5. **今の案件で新しい管理方式を追加する必要はない。** 既に `docs/HANDOFF.md` と各検証記録・正式Drive保存先がある。別の状態ファイルを追加すると現在地を二重管理することになる。既存HANDOFFにも履歴の「最新」という見出しが複数残っているため、今後の記録では現在地と過去の履歴を明確に区別する。新方式の導入を、その整理の代わりにはしない。

検証は合成データによる機能試験とソース確認であり、全入力に対する安全性認証ではない。特に、実際のDrive保存、利用者の意図、作業範囲の網羅性、現地の状況は、このCLIの試験では証明できない。
