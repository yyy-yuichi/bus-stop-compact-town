# 徒歩圏の事前焼き込み設計

作成日：2026-09-09 / 更新：2026-09-09（勾配モデルを追加）/ 状態：レビュー待ち

## 1. 背景と目的

現在の徒歩圏機能は、おのだサンパーク周辺の7停留所だけの試作である。道路グラフ
（`public/data/walking-onoda.json`、2,818ノード・3,023区間・205KB）をブラウザへ配信し、
クライアント側で Dijkstra を実行している。

これを山口県全域の**3,946停留所**へ広げる。バス停の出典も、収録漏れのある
OSM（1,085件）から**国土数値情報のバス停留所データ（P11）**へ切り替える。ただしグラフ配信のまま広げると破綻するため、
**バス停ごとに徒歩圏を事前計算（焼き込み）して配信する方式へ切り替える。**

目的は3つ。

1. 全バス停で徒歩圏を表示できるようにする
2. 「その徒歩圏に任意の地物（ショッピングモール等）が入っているか」を
   **クライアント側で判定できる**ようにする
3. **勾配を歩行時間に反映する**。平坦な距離だけで徒歩圏を描くと、
   坂の多い地域で実態と乖離する
4. **バス停の収録漏れをなくす**。OSMは萩市北部・阿武町・須佐が0件だった

2番目により、施設データの追加・差し替えが徒歩圏の再計算と無関係になる。
現在 `shopping.geojson` が19件しかない問題は、焼き込みのブロッカーではなくなる。

## 2. 方式の判断根拠

### なぜグラフ配信を続けないか

全1,085停留所を含む範囲は約138km × 59km で、試作範囲の約1,100倍の面積。
停留所を含むタイルだけに絞っても157枚・約31MBになる。さらにタイル境界では
徒歩10分（約800m）ぶんの道路が切れるため、1km前後の重複を持たせる必要があり、
それでも縫い目の不自然さは残る。

### 焼き込みの実測値

UIのバンドは徒歩5分・10分・15分の3種、速度は3または4km/h。
**最大バジェットは 時速4km × 15分 = 1000m** であり、これで焼けば
どのバンドもクライアント側で切り出せる。

試作グラフの7停留所を実際に焼いて測定した。

| 停留所 | セグメント数 | 生JSON | gzip |
|---|---|---|---|
| サンパークおのだ | 384 | 19.3KB | 4.6KB |
| 中川通り | 342 | 17.3KB | 4.3KB |
| 硫酸町 | 281 | 14.2KB | 3.6KB |
| **中央値** | | **16.6KB** | **4.1KB** |

### バス停データをP11へ切り替える根拠

`raw_data/P11-22_35.geojson`（国土数値情報 バス停留所 2022年度・山口県）を
既存のOSM由来データと突き合わせて測定した。

| 緯度帯 | P11 | OSM |
|---|---|---|
| 南部（下関〜宇部） | 2,211 | 728 |
| 中部（山口〜岩国） | 2,091 | 357 |
| **北部（萩・阿武・須佐）** | **116** | **0** |
| 合計 | 4,418 | 1,085 |

- OSMが0件だった北部が埋まる
- 名称・事業者名の充足率100%（17事業者）、系統名も全件に最低1本
- 岩国市605・宇部市450・山口市396・周南市371と、**コミュニティバスが入る**。
  OSMではほぼ拾えない領域である
- **道路への近さはOSMより良い。** 試作範囲で道路グラフへ実際にスナップした結果、
  中央値はOSMの5mに対しP11は1m、30m以内に収まるのは100%（23点）。
  P11は道路中心線上、OSMは路側のポール位置という置き方の差である

弱点は2022年度時点であること（廃止・新設が反映されない）と、
一意IDを持たないこと（4.6節で対処する）。

### バンド幅とサイズの実測

50m分割・折り返し分割・実標高をすべて適用したうえで、
サンパークおのだを実際に焼いて測定した（推定ではなく実測値）。

| | 10分（1000m未満） | **15分（1000m）** | 倍率 |
|---|---|---|---|
| セグメント | 539本 | **917本** | 1.70× |
| 生 | 99.2KB | **168.6KB** | 1.70× |
| gzip | 8.6KB | **14.8KB** | 1.72× |

面積比なら2.25倍になるはずだが**1.70倍で収まる**。道路網は外周ほど疎になり、
途中で行き止まるためである。試作bboxの境界から50m以内の点は0/1834であり、
**境界切れによる過小評価はない。**

### 出力形式と座標精度

同じ焼き込み結果を4通りで書き出して実測した。

| | 生 | gzip | 全体(1085) |
|---|---|---|---|
| GeoJSON・座標6桁 | 168.6KB | 14.8KB | 179MB |
| **GeoJSON・座標5桁** | **164.9KB** | **13.3KB** | **175MB** |
| コンパクト配列・座標6桁 | 48.2KB | 11.6KB | 51MB |
| コンパクト配列・座標5桁 | 44.6KB | 10.4KB | 47MB |

**座標は5桁（約1.1m精度）とする。** スナップ判定30m、施設判定25m、
地図描画のいずれにも十分であり、gzip後で1割減る。

**形式はGeoJSONを採用する。** コンパクト配列より生で3.7倍大きいが、
175MBはGitHub Pagesの1GB制限に十分収まる。gzip後の差は13.3KB対10.4KBで
利用者にはほぼ体感できない。QGISやgeojson.ioでそのまま開けることと、
本リポジトリの他のデータがすべてGeoJSONである一貫性を優先する。
**県内全バス停の徒歩圏データそのものが再利用可能な成果物になる。**

## 3. 成果物の形式

`data/walk/<stop-id>.geojson` を1停留所1ファイルとする。

**停留所IDは座標を小数5桁で表した `<経度>_<緯度>` とする**（例 `131.17228_33.98546`）。
ファイル名はこれに `.geojson` を付けたもの。P11は一意IDを持たないため合成する（4.6節）。

**このファイル群はgitに置かず、GitHubのReleaseアセットで配布する**（3.2節）。

GeoJSONのFeatureCollectionとし、3種類のFeatureを `role` で区別する。
これにより、QGIS等へそのまま読み込んで意味のある図になる。

```json
{
  "type": "FeatureCollection",
  "version": 1,
  "stop_id": "node/5127585172",
  "budget": 1000,
  "features": [
    { "type": "Feature", "properties": { "role": "stop", "name": "サンパークおのだ" },
      "geometry": { "type": "Point", "coordinates": [131.1760, 33.9870] } },
    { "type": "Feature", "properties": { "role": "snap", "gap": 8.4 },
      "geometry": { "type": "LineString", "coordinates": [[131.1760,33.9870],[131.1761,33.9872]] } },
    { "type": "Feature",
      "properties": { "role": "segment", "d1": 12, "d2": 47, "grade": -6, "steps": false },
      "geometry": { "type": "LineString", "coordinates": [[131.1760,33.9870],[131.1764,33.9873]] } }
  ]
}
```

`version` / `stop_id` / `budget` はFeatureCollectionの
foreign member として置く（RFC 7946 §6.1 が許容している）。

`role: "segment"` のFeatureが徒歩圏の本体で、次のpropertyを持つ。

- **`d1` / `d2`** — 始点・終点の**等価平坦距離**（4節）。実際の道のりではなく、
  同じ時間で平坦地を歩ける距離。整数メートル。
  バス停から最寄り道路までの接続距離（`snap` の `gap`）を含む
- **`grade`** — 始点→終点方向の符号付き勾配（整数の百分率）。逆向きは符号を反転する
- **`steps`** — `highway=steps` に由来するか（真偽値）

**急勾配であることは `grade` の数値で表し、真偽値は持たせない。**
閾値は政策判断であり（4.5節のとおり5%が基準だが8%という根拠もある）、
真偽値を焼き込むとその判断が固定される。数値で持てば、
クライアントが5%でも8%でも選べ、**焼き直しが不要**になる。

- **各セグメントの内部では距離が線形に変化することを保証する**（5.3節）
- **座標は小数5桁**（約1.1m精度）。`budget` は最大バンドの 1000m
  （時速4km × 15分）で、5分・10分は同じファイルから切り出す

道路網を歩いて到達できない停留所（最寄り道路まで30m超）はファイルを生成しない。
クライアントは404を「接続を確認できなかった停留所」として扱う。

### 3.2 配布方法：Releaseアセット

609MBを3,946ファイルとしてgitに置くと、**再焼成のたびに履歴が同じだけ増える。**
JSONは中身が全面的に変わるため差分も圧縮も効かず、2回目で1.2GB、3回目で1.8GBとなり
クローンが現実的でなくなる。公開サイトの1GBは強制だが、リポジトリの1GBは推奨であり、
先に破綻するのは履歴のほうである。

そこで**焼いた結果を1本のtarにまとめ、GitHubのReleaseアセットとして配布する。**
Releaseアセットは1ファイル2GBまでで、リポジトリ容量とは別枠、総量の制限もない。

- 焼き込みは `work/walk/` へ出力し、`work/walk-data-<日付>.tar.gz` にまとめる
- Releaseへアップロードする
- **gitに置くのは版を指す小さなマニフェストだけ。**
  `public/data/walk-release.json` に `{tag, asset, sha256, count}` を記録する
- `npm run data:fetch` がマニフェストを読み、tarを取得・SHA256検証・展開して
  `public/data/walk/` へ置く。`public/data/walk/` は `.gitignore` する
- CIは `npm run build` の前に `npm run data:fetch` を実行する。
  **取得先はGitHub自身**であり、国土地理院やGeofabrikを叩くわけではないため、
  外部データ取得の作法（Global Constraints）には抵触しない
- ローカル開発とCIが同じ経路を通るため、分岐が増えない

## 4. 勾配モデル

### 4.1 標高データの入手

**OSMからは取得できない。** 試作範囲（小野田周辺）でOverpassに実測を投げた結果：

| 項目 | 件数 |
|---|---|
| `highway` を持つway | 695 |
| うち `incline` タグあり | **0** |
| `bridge` タグあり | 17 |
| `highway=steps` | 6 |

`incline=*` の仕様自体はあるが、日本の一般道ではほぼ付いていない。
OSMは地形を持たない設計であり、標高は別データと組み合わせるのが定石である。

**国土地理院の標高タイルを使う。**

```
DEM5A  https://cyberjapandata.gsi.go.jp/xyz/dem5a/{z}/{x}/{y}.txt  5mメッシュ・航空レーザ・最大z15
DEM10B https://cyberjapandata.gsi.go.jp/xyz/dem/{z}/{x}/{y}.txt    10mメッシュ・精度5m以内・最大z14
```

中身はカンマ区切り256個 × 256行の平文テキスト（単位m・小数第2位、
無効値は `e` の文字）。**GDALもnumpyも不要で、標準ライブラリだけで読める。**

**DEM5A（z15）を第一候補、DEM10B（z14）を欠測時のフォールバックとする。**
DEM10Bは鉛直精度が5m以内であり、30mの区間に当てると勾配が最大17%ずれるため、
徒歩圏の判定には粗い。

取得量の試算（バジェット1000m + 余裕の範囲）：

| | 1タイル | 必要枚数 | 概算 |
|---|---|---|---|
| DEM5A (z15) | 約1.0km四方 | 約993枚 | 約388MB |
| DEM10B (z14) | 約2.0km四方 | 約420枚 | 約165MB |

バジェットを10分から15分へ広げてもタイルは870枚から993枚（+14%）にしか増えない。
バス停どうしの徒歩圏が重なるため、半径を1.5倍にしてもタイル数はほぼ増えない。

一度きりの取得なので、**ディスクにキャッシュして再取得しない。**
国土地理院への負荷を抑えるため、逐次取得とし並列度を上げない。

### 4.2 歩行速度と勾配：Toblerの登山関数を正規化して使う

```
W = 6 · exp(−3.5 · |i + 0.05|)     W: 速度(km/h)、i: 勾配(高低差/水平距離)
```

Waldo Toblerが1993年にImhofの実測データから定式化したもの。
平坦で約5.0km/h、最速6km/hは勾配−5%（ゆるい下り）で出る。
平坦が最速ではない点と、上りと下りで非対称な点が実測に基づく特徴である。

そのまま使うと平坦5km/hになり、現行UIの3/4km/hと食い違う。
**平坦時の値で正規化し、勾配による相対的な劣化の形だけを借りる。**

```
補正係数 = Tobler(i) / Tobler(0) = exp(−3.5 · (|i+0.05| − 0.05))
等価平坦距離 = 実距離 ÷ 補正係数
```

**この係数は歩行速度に依存しない。** したがって焼き込むのは等価平坦距離でよく、
クライアントは従来どおり選択速度（3または4km/h）で割るだけでよい。
**速度セレクタも5分/10分/15分のバンド切り替えもクライアント側で完結する。**

平坦時の係数がちょうど 1.000000 になることを検算済みであり、
勾配ゼロなら現行の実装と完全に一致する（7節の検証で担保する）。

### 4.3 徒歩圏の定義：往復の悪いほう

谷底のバス停は下り方向の到達範囲が広く出るが、帰りは上りになる。
「バス停から歩いて行ける」は暗黙に「帰ってこられる」を含むため、
**往路と復路の厳しいほうを採用する。**

これによりモデルが単純化する。往復の悪いほうを取ると、

```
max( f(i), f(−i) ) = exp(3.5 · |i|)
```

となり、**下りの得が往路と復路で相殺されて勾配の絶対値だけが効く。**
検算では −10% の係数 1.419 が +10% と完全に一致する。

結果として**区間コストが方向によらず対称になる**ため、次が成り立つ。

- **Dijkstraは1回でよい**（往路・復路の2回が不要）
- **距離場が最短経路場のまま**なので、経路表示の距離場降下（6.3節a）が使える
- **折り返し分割の式も元のまま**。`L` が `L · exp(3.5·|i|)` に変わるだけ

したがって区間の等価平坦距離は次の一行で決まる。

```
L_eff = L · exp(3.5 · |i|)
```

**近似について。** 区間ごとに悪いほうを採ると、往路と復路で別ルートを使えば
得になるケースを取りこぼし、理論上の `max(最適往路, 最適復路)` よりやや厳しく出る。
これは安全側の誤差であり、同じ道を往復する高齢者の実態にはむしろ即している。
`ponytail:` コメントで近似であることと、2回Dijkstraへ移行する手順を残す。

### 4.4 標高のサンプリング

区間の両端で標高を引き、その差と水平距離から勾配を求める。ただし次を守る。

**50mを超える区間は50m以下に分割してから標高を引く。** 区間全体の平均勾配で
済ませると、上って下る道が平坦と同じ扱いになる。試作グラフの区間長は
中央値14.3m・平均26.8m・最大635mで、50m超は14%（420/3,023本）。
50m分割なら区間数は1.21倍で済む。25m分割は1.63倍になり、精度の利得に見合わない。

**橋・トンネルは勾配を両端の線形補間で置き換える。** DEMは地表面標高であり、
橋の下の谷や川床を読んで存在しない絶壁が出る。試作範囲だけで橋が17本ある。
`bridge` / `tunnel` タグ、または `layer` が0以外のwayが対象。

**勾配は ±30% でクランプする。** DEMの誤差が短い区間に乗ると異常な勾配が出る。
実在の道路が30%を超えることはまれである。

**階段（`highway=steps`）はDEMから勾配を取らない。** 階段の上でDEMを引いても
意味のある値にならない。4.5節の警告として扱い、`steps` プロパティを真にする。

**バス停から最寄り道路への接続（`snap.gap`、30m以内）は平坦として扱う。**
そもそも直線近似であり、ここに勾配を入れても精度は上がらない。

### 4.5 勾配と階段の警告

連続的な速度モデルに加えて、閾値による警告を出す。
神戸市バリアフリー道路整備マニュアル等では歩道の縦断勾配5%以下が基準であり、
根拠は車いすの自力登坂限界が8.5%であることによる。

- セグメントの `grade` が **±5%** を超える場合、経路上に急勾配があるとして警告する
- `steps` が真のセグメントが経路上にある場合、階段があるとして警告する

閾値はクライアント側で判定するため、8%へ変えたい場合も**焼き直しは不要**である。

### 4.6 バス停データの生成

`raw_data/P11-22_35.geojson`（国土数値情報 P11・2022年度・山口県）を
`public/data/bus_stop.geojson` へ変換する。

**座標を小数5桁に丸めた `<経度>_<緯度>` を一意IDとし、同じIDの点を1件に統合する。**
4,418件が3,946件になる（472件を統合）。

**名称を統合の鍵に含めない。** 測定の結果、同一座標に載る420グループのうち
名称が食い違うのは25件だけで、その中身が名称を鍵にすべきでない理由そのものだった。

```
斉木病院前 / 斎木病院前          表記ゆれ
下管蓋 / 下菅蓋                 誤字
県庁前 / 山口県庁前              事業者ごとの表記差
```

名称を鍵に含めると、この表記ゆれのせいで同一地点が統合されずに残る。

座標5桁の粒度は北緯34度で約1.0m × 1.2mであり、上下線（10〜20m離れ）は
統合されず別停留所のまま残る。統合後、「同名かつ50m以内」の対は0組になり、
追加の統合処理は不要である。

統合した点の属性は失わずに配列で持つ。

```json
{ "type": "Feature", "id": "131.17228_33.98546",
  "properties": { "name": "堀越", "names": ["堀越"],
                  "operators": ["宇部市", "美祢市"], "routes": ["…"] },
```

### 5.1 道路データの取得

OSM API 0.6 の `/map` は bbox 0.25 平方度が上限で、県全域（約0.795平方度）は
取得できない。**Geofabrik の中国地方 pbf から山口県範囲を切り出す。**

取得元・取得日・SHA256 は現行と同様にマニフェストへ記録する。

なお現行の `scripts/sanitize-walking-source.py` が保持するタグ集合には
`bridge` / `tunnel` / `layer` が含まれていない。4.4節の橋・トンネル処理に
必要なため、**保持タグへ追加する。**

### 5.2 グリッドバケットによる最寄り道路探索

現行の `calculateWalk`（`walking.ts:71`）は全区間を線形走査して最寄り区間を探す。
試作規模（3,023区間 × 7停留所 ≒ 2万回）なら一瞬だが、県全域では
**約150万区間 × 1,085停留所 ≒ 16億回**となり成立しない。

県全体を500m四方のマス目に区切り、`{(マスX, マスY): [区間番号]}` という辞書を
1回だけ構築する。検索時はバス停の属するマスと周囲8マス（3×3）だけを調べる。

マスは緯度経度をそのまま割って求める。山口県の緯度（北緯34度前後）では
経度1度が約92km、緯度1度が約111kmなので、**経度0.0055度・緯度0.0045度**を
1マスとすれば、およそ500m四方になる。厳密な正方形である必要はない。

- マス1つあたりの区間数はせいぜい数十本なので、**150万本 → 100〜200本**に減る
- スナップ閾値が30m（`walking.ts:76`）なので、500mマス＋3×3の探索で取りこぼさない
- **マスより長い区間は、外接矩形が触れる全マスに登録する。**
  両端のマスだけに登録すると、区間の中ほどに立ったとき見つからない
- 空のマスは辞書に載らないため、県土の大半が海や山でも無駄が出ない

四分木ではなくグリッドを選ぶ理由は、**検索半径が30mに固定**だからである。
半径が既知なら3×3の走査で必ず足り、四分木の密度適応は何も買わない。
また、スナップ対象は点ではなく線分なので、点用のKD木・四分木では
「最寄りノード」しか出ず、最寄り区間とは別物になる。

### 5.3 距離場の折り返し分割

**これを省くと最大で区間長の半分の誤差が出る。**

区間 A—B（等価平坦長 L_eff）上の、A から割合 t の地点までの最短距離は次の通り。

```
f(t) = min( d[A] + t·L_eff,  d[B] + (1−t)·L_eff )
```

環状路では A と B に別ルートで到達するため、区間の内部で2つの経路が交差し、
そこが**その区間で最も遠い地点（山型の頂点）**になる。

```
        バス停
          ●
         ╱ ╲
   100m ╱   ╲ 120m
       ╱     ╲
      A ━━━━━ B    ← 距離は 100 → 130（75%地点）→ 120 と推移
```

両端の値（100 と 120）だけ保存して線形補間すると、75%地点で 115m と計算されるが
真値は 130m で、**15m の過小評価**になる。最大誤差は `(L² − Δ²) / 2L`、
両端が等距離のとき区間長の半分。区間長は中央値14.3mだが最大635mまであり、
施設判定の閾値が「道路から25m以内」であるため、この誤差は無視できない。

分割すべき地点は2種類ある。どちらも距離関数の折れ点である。

1. **山型の頂点**（両方向に通行可で、両端が到達可能で、`|d[A] − d[B]| < L_eff` のとき）

   ```
   t* = (d[B] − d[A] + L_eff) / (2·L_eff)     頂点での距離 = (d[A] + d[B] + L_eff) / 2
   ```

2. **出発地点が区間の内部にある場合のスナップ点**（谷型の底）。
   スナップ点から両方向へ距離が増えるため、ここも折れ点になる。

分割後は各断片の内部が単調な直線になり、端点からの線形補間が厳密になる。

4.3節により区間コストは方向によらず対称なので、往復の悪いほうを採っても
この式は変わらない。試作範囲での実測では、到達384セグメント中44本（11%）が
山型に該当した。ただしこの計測は歩行者一方通行のフラグを考慮していない
粗いものなので、実際の該当数はこれよりやや少ない。

### 5.4 処理の流れ

1. pbf から山口県範囲を切り出し、既存ロジックで歩行グラフを構築
2. 50mを超える区間を分割（4.4節）
3. 標高タイルを取得・キャッシュし、各区間の勾配を求める（4.1・4.4節）
4. 等価平坦長 `L_eff = L · exp(3.5·|i|)` を計算（4.3節）
5. グリッドバケットを構築（5.2節）
6. P11からバス停データを生成（4.6節）
7. 各停留所について、最寄り区間へスナップ（30m以内）→ Dijkstra（バジェット1000m）
8. 到達区間をバジェットでクリップし、折れ点で分割（5.3節）
9. `work/walk/` へ1停留所1ファイルとして出力し、tarにまとめてReleaseへ（3.2節）

## 7. 検証方法

**現行実装との回帰テストを正しさの根拠とする。**

既存の `scripts/test-walking.mjs`（`npm run test:walking`）を流用する。

**勾配ゼロでの完全一致を最重要の検証とする。** すべての区間の勾配を0として
焼いた場合、4.2節の補正係数はちょうど1.000000になるため、
**現行の `calculateWalk` + `reachableLines` の結果と完全に一致しなければならない。**
これが通れば、焼き込みの骨格が正しいことの証明になる。具体的には試作7停留所で、

1. 焼いたセグメントの総延長が現行と一致する（5分・10分・15分すべて）
2. おのだサンパークへの到達距離が現行と一致する
3. 5分の徒歩圏が10分に、10分の徒歩圏が15分に含まれる

そのうえで勾配モデルを個別に検証する。

4. **正規化の検算** — 補正係数が勾配0でちょうど1.0、−5%で最小（0.839）になる
5. **往復対称性** — `max(f(i), f(−i))` が `exp(3.5|i|)` と一致し、
   +10%と−10%が同じ係数になる
6. **折り返し分割** — 環状路を持つ合成グラフで山型の頂点が分割され、
   分割後の線形補間が真値と一致する（5.3節の数式による）
7. **スナップ点の分割** — スナップ点が区間の内部にある場合、そこでも分割される
8. **橋・トンネルの平坦化** — 谷を渡る橋で、DEMの地表面標高ではなく
   両端の線形補間が使われる
9. **勾配のクランプ** — DEMの異常値が±30%に収まる
10. **標高タイルの解釈** — 無効値 `e` を含むタイルを正しく扱う

既存テストの合成グラフ検証（クリッピング、交差の非接続、
歩行者一方通行、到達不能判定）はそのまま維持する。

## 9. 既知の天井

- **バジェットが1000m固定** — 「時速4km × 15分」ちょうどで焼く。
  後から20分バンドや時速5kmを追加すると**全件の焼き直しが必要**になる。
  10分から15分への拡張はセグメント数が1.70倍で済んだが、
  さらに広げると同様に増えるため、今は最大バンドちょうどで詰めて焼く
- **区間ごとに往復の悪いほうを採る近似**（4.3節）— 往路と復路で別ルートを
  使えば得なケースを取りこぼす。安全側の誤差。厳密にするには
  往路・復路の2回Dijkstraと、`out`/`max` の2値をセグメントに持たせる必要がある
- **Toblerは登山者のデータ** — 都市部の高齢者には楽観的な可能性がある。
  ただし正規化して相対的な劣化の形だけを借りるため、
  平坦時は現行と完全に一致する。日本の高齢者歩行データで
  係数を較正できれば精度が上がる
- **勾配は区間の平均** — 50m以下に分割したうえでの平均であり、
  区間内の細かい起伏は反映しない
- **OSM更新への追随** — 道路データが更新されたら1,085件を焼き直す。
  標高タイルはキャッシュが効くため、再取得は不要
- **公開サイトの余裕が413MB** — isochroneが609MBを占め、上限1024MBに対して
  余裕は4割。停留所が増えるか20分バンドを足すと超える。
  そのときはコンパクトな配列形式へ落とす（生で3.7倍軽い。609MB→165MB）。
  クライアント側の変更は限定的であり、**その判断を今する必要はない**
- **バス停データが2022年度時点** — 廃止路線が残り、新設が入っていない可能性がある。
  OSMと突き合わせて差分を見る余地があるが、本設計では行わない
- **合成IDが座標由来** — P11の年度が変わって座標が動くとIDも変わり、
  焼いたファイル名も変わる。年度更新時は全件を焼き直す前提とする

## 10. ライセンスの整理（解決済み）

焼き込みデータは OSM と国土地理院の標高タイルの双方に由来するため、
両者の条件が両立するかを確認した。**両立する。**

**OSM側** — 焼き込み結果はOSMのジオメトリから導出した派生データベースにあたるため、
ODbL 1.0 の継承条項（第4.4条）により**成果物もODbL 1.0で提供する**。
`about.html` に反映済み（2026-09-09）。

**国土地理院側** — 標高タイル DEM5A / DEM10B は
[地理院タイル一覧](https://maps.gsi.go.jp/development/ichiran.html)において
**「基本測量成果以外」（第2類）**に区分され、**出典の記載のみで利用可能**である。
基本測量成果に必要な測量法に基づく申請は**不要**。

[国土地理院コンテンツ利用規約](https://www.gsi.go.jp/kikakuchousei/kikakuchousei40182.html)
には**公共データ利用規約（PDL1.0）**が適用される。要件は次の2点。

1. 出典を記載する（「出典：国土地理院ウェブサイト」）
2. 編集・加工した場合は、出典とは別に**加工した事実**を記載し、
   国土地理院が作成したかのような表示をしない

**両立する理由** — PDL1.0 は表示を求めるのみで**継承条項を持たない**。
したがってODbLの継承条項と衝突せず、
**成果物をODbL 1.0で配布しつつ、国土地理院の出典と加工事実を併記すれば要件を満たす。**

**国土数値情報側** — バス停留所データ（P11）には
[国土数値情報ダウンロードサイト利用規約](https://nlftp.mlit.go.jp/ksj/other/agreement.html)
により**公共データ利用規約（PDL1.0）**が適用される。要件は国土地理院と同じく、
出典の記載と、編集・加工した場合の加工内容の記載であり、**継承条項を持たない。**

3者はいずれも衝突しない。継承条項を持つのはODbLだけで、他の2つは表示を求めるのみである。
**成果物をODbL 1.0で配布し、3者の出典と加工事実を併記すれば要件を満たす。**

なお公開前に、6.5節の文言が各要件を満たしているか最終確認すること。
