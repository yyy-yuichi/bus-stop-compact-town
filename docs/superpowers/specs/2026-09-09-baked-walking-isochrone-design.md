# 徒歩圏の事前焼き込み設計

作成日：2026-09-09 / 状態：レビュー待ち

## 1. 背景と目的

現在の徒歩圏機能は、おのだサンパーク周辺の7停留所だけの試作である。道路グラフ
（`public/data/walking-onoda.json`、2,818ノード・3,023区間・205KB）をブラウザへ配信し、
クライアント側で Dijkstra を実行している。

これを山口県全域の1,085停留所へ広げる。ただしグラフ配信のまま広げると破綻するため、
**バス停ごとに徒歩圏を事前計算（焼き込み）して配信する方式へ切り替える。**

目的は2つ。

1. 全バス停で徒歩圏を表示できるようにする
2. 「その徒歩圏に任意の地物（ショッピングモール等）が入っているか」を
   **クライアント側で判定できる**ようにする

2番目が重要で、施設データを焼き込まないことで、**施設の追加・差し替えが
徒歩圏の再計算と無関係になる**。現在 `shopping.geojson` が19件しかない問題は、
焼き込みのブロッカーではなくなる。

## 2. 方式の判断根拠

### なぜグラフ配信を続けないか

全1,085停留所を含む範囲は約138km × 59km で、試作範囲の約1,100倍の面積。
停留所を含むタイルだけに絞っても157枚・約31MBになる。さらにタイル境界では
徒歩10分（約800m）ぶんの道路が切れるため、1km前後の重複を持たせる必要があり、
それでも縫い目の不自然さは残る。

### 焼き込みの実測値

試作グラフの7停留所を、UIの最大バジェット（時速4km × 10分 = 666.7m）で
実際に焼いて測定した。

| 停留所 | セグメント数 | 生JSON | gzip |
|---|---|---|---|
| サンパークおのだ | 384 | 19.3KB | 4.6KB |
| スポーツセンター前 | 356 | 18.0KB | 4.3KB |
| 中川通り | 342 | 17.3KB | 4.3KB |
| 硫酸町 | 281 | 14.2KB | 3.6KB |
| **中央値** | | **16.6KB** | **4.1KB** |

後述の折り返し分割で約11%増えるため、**1停留所あたり約18.5KB**を見込む。

- 全体：約19.6MB（gzip 約4.6MB）。GitHub Pages の1GB制限に対して余裕がある
- 1クリックあたりの転送：**205KB → 約18.5KB（約1/11）**
- 上記は市街地の数値であり、県内の大半を占める郊外・山間部はさらに小さくなる

## 3. 成果物の形式

`public/data/walk/<sanitized-id>.json` を1停留所1ファイルとする。
停留所IDは `node/5127585172` の形式なので、`/` を `-` に置換して
`node-5127585172.json` とする。

```json
{
  "version": 1,
  "id": "node/5127585172",
  "coordinate": [131.1760, 33.9870],
  "budget": 666.7,
  "snap": { "point": [131.1761, 33.9872], "gap": 8.4 },
  "segments": [[131.1760, 33.9870, 131.1764, 33.9873, 12, 47]]
}
```

- `segments` の各要素は `[lon1, lat1, lon2, lat2, 距離1, 距離2]`
- 距離はバス停からの徒歩距離（整数メートル）。座標は小数6桁
- `snap` は最寄り道路への接続点と接続距離。地図上の破線描画に使う
  （現行 `WalkingPanel.tsx:52`）
- **`segments` の距離には、バス停から最寄り道路までの接続距離（`snap.gap`）を
  含める。** 現行の `calculateWalk` と同じ扱いであり、`about.html` の
  「その接続距離も時間に含めます」という記述とも一致する
- **各セグメントの内部では距離が線形に変化することを保証する**（4.3節）

道路網を歩いて到達できない停留所（最寄り道路まで30m超）はファイルを生成しない。
クライアントは404を「接続を確認できなかった停留所」として扱う。

## 4. 焼き込みパイプライン

新規 `scripts/bake-walking.py`。既存 `scripts/build-walking-pilot.py` の
`can_walk` / `node_open` / `meters` をそのまま再利用し、標準ライブラリのみで書く。

### 4.1 道路データの取得

OSM API 0.6 の `/map` は bbox 0.25 平方度が上限で、県全域（約0.795平方度）は
取得できない。**Geofabrik の中国地方 pbf から山口県範囲を切り出す。**

取得元・取得日・SHA256 は現行と同様にマニフェストへ記録し、
ODbL 1.0 の帰属表示を維持する。

### 4.2 グリッドバケットによる最寄り道路探索

現行の `calculateWalk`（`walking.ts:71`）は全区間を線形走査して最寄り区間を探す。
試作規模（3,023区間 × 7停留所 ≒ 2万回）なら一瞬だが、県全域では
**約150万区間 × 1,085停留所 ≒ 16億回**となり成立しない。

県全体を500m四方のマス目に区切り、`{(マスX, マスY): [区間番号]}` という辞書を
1回だけ構築する。検索時はバス停の属するマスと周囲8マス（3×3）だけを調べる。

マスは緯度経度をそのまま割って求める。山口県の緯度（北緯34度前後）では
経度1度が約92km、緯度1度が約111kmなので、**経度0.0055度・緯度0.0045度**を
1マスとすれば、およそ500m四方になる。厳密な正方形である必要はない。

- マス1つあたりの区間数はせいぜい数十本なので、**150万本 → 100〜200本**に減る
- スナップ閾値が30m（`walking.ts:76`）なので、500mマス＋3×3の探索で取りこぼさない
- **マスより長い区間は、外接矩形が触れる全マスに登録する。**
  両端のマスだけに登録すると、区間の中ほどに立ったとき見つからない
- 空のマスは辞書に載らないため、県土の大半が海や山でも無駄が出ない

四分木ではなくグリッドを選ぶ理由は、**検索半径が30mに固定**だからである。
半径が既知なら3×3の走査で必ず足り、四分木の密度適応は何も買わない。
また、スナップ対象は点ではなく線分なので、点用のKD木・四分木では
「最寄りノード」しか出ず、最寄り区間とは別物になる。

### 4.3 距離場の折り返し分割

**これを省くと最大で区間長の半分の誤差が出る。**

区間 A—B（長さ L）上の、A から割合 t の地点までの最短距離は次の通り。

```
f(t) = min( d[A] + t·L,  d[B] + (1−t)·L )
```

環状路では A と B に別ルートで到達するため、区間の内部で2つの経路が交差し、
そこが**その区間で最も遠い地点（山型の頂点）**になる。

```
        バス停
          ●
         ╱ ╲
   100m ╱   ╲ 120m
       ╱     ╲
      A ━━━━━ B    ← 距離は 100 → 130（75%地点）→ 120 と推移
```

両端の値（100 と 120）だけ保存して線形補間すると、75%地点で 115m と計算されるが
真値は 130m で、**15m の過小評価**になる。最大誤差は `(L² − Δ²) / 2L`、
両端が等距離のとき区間長の半分。OSMの区間長は20〜50mなので最大10〜25mずれる。
施設判定の閾値が「道路から25m以内」であるため、この誤差は無視できない。

分割すべき地点は2種類ある。どちらも距離関数の折れ点である。

1. **山型の頂点**（両方向に通行可で、両端が到達可能で、`|d[A] − d[B]| < L` のとき）

   ```
   t* = (d[B] − d[A] + L) / (2L)      頂点での距離 = (d[A] + d[B] + L) / 2
   ```

2. **出発地点が区間の内部にある場合のスナップ点**（谷型の底）。
   スナップ点から両方向へ距離が増えるため、ここも折れ点になる。

分割後は各断片の内部が単調な直線になり、端点からの線形補間が厳密になる。

試作範囲での実測では、到達384セグメント中44本（11%）が山型に該当した。
ただしこの計測は歩行者一方通行のフラグを考慮していない粗いものなので、
実際の該当数はこれよりやや少ない。

### 4.4 処理の流れ

1. pbf から山口県範囲を切り出し、既存ロジックで歩行グラフを構築
2. グリッドバケットを構築
3. 各停留所について、最寄り区間へスナップ（30m以内）→ Dijkstra（バジェット666.7m）
4. 到達区間をバジェットでクリップし、折れ点で分割
5. 1停留所1ファイルとして出力

## 5. クライアント側の変更

### 5.1 削除するもの

`src/walking.ts` から以下が消える。**経路探索がクライアントから丸ごと無くなる。**

- `calculateWalk`
- `MinHeap`
- `validateGraph`
- `WalkingGraph` / `WalkResult` / `Edge` 型
- `inPilot`

`project` / `interpolate` / `distance` はそのまま使う。

### 5.2 変更するもの

**`reachableLines`** — Dijkstra の結果ではなく焼いたセグメント配列を受け取り、
バジェットで切るだけの関数に縮小する。各セグメントの内部は線形なので、
`d1` / `d2` から補間して切ればよい。

**`reachFacility`** — 入力を `WalkResult` からセグメント配列に差し替える。
判定ロジック（施設外形を道路へ投影し、25m以内の道路点までの距離を取る）は
そのまま維持する。走査対象が3,023区間から約380セグメントへ減るため、
現行より速くなる。

**`useWalkingData`**（`WalkingPanel.tsx:7`）— 現在は起動時にグラフと
`shopping.geojson` を一括取得している。これを次のように分ける。

- `shopping.geojson` は従来どおり全体を1回取得する
- 徒歩圏ファイルは**選択中の停留所IDに応じて遅延取得**する
- `graph.facility_ids` による施設の絞り込みを廃止し、**全施設を判定対象にする**
  （クライアント判定を可能にすることが本設計の目的のため）

### 5.3 洗い出しで見つかった追加の依存

実装箇所を確認したところ、`pilot_stops` と `parents` に依存する箇所が
3つ見つかった。いずれも対処が必要である。

**(a) 経路表示** — `showPath` は `reach.path` を描画する（`WalkingPanel.tsx:57`）。
これは現在 `pathTo` が Dijkstra の親ポインタ（`parents`）をたどって作っている。
焼き込み後は親ポインタが存在しない。

対処：**距離場を降下して復元する。** セグメントの端点を座標でハッシュして
隣接索引を作り、目的地点から「距離がより小さい隣接端点」へ順にたどる。
焼いたものは最短距離場なので、この降下は最短経路と一致する。
追加のバイト数は不要で、索引構築は約380セグメントに対して一度だけ。

**(b) 停留所セレクタ** — 「出発するバス停を変える」の `<select>` は
`data.graph.pilot_stops` を列挙している。1,085件を並べるのは非現実的なため、
**このセレクタと「試作地域へ移動」ボタンを削除する。**
`BusStopLayer.tsx:79` がすでに地図上の選択を `id` として渡しているので、
停留所の切り替えは地図が担う。

**(c) 試作範囲の案内文** — `inPilot` が false のときの
「現在は、おのだサンパーク周辺の7停留所で試せます」という分岐が不要になる。
代わりに、徒歩圏ファイルが404だった場合の「この停留所と歩ける道路の接続を
確認できませんでした」という既存メッセージへ寄せる。

### 5.4 ドキュメントの更新

`public/about.html` の「徒歩圏の計算方法」（23〜26行目）と
データ配布リンク（39行目）を更新する。OSMの取得日・範囲・
ODbL 1.0 の帰属表示を新しいものに差し替える。
焼き込み済みデータも OSM の派生物であるため、帰属表示は維持する。

## 6. 検証方法

**現行実装との回帰テストを正しさの根拠とする。** これが通れば
焼き込みが正しいことの証明になる。

既存の `scripts/test-walking.mjs`（`npm run test:walking`）を流用し、
試作範囲の7停留所について次を確認する。

1. 焼いたセグメントの総延長が、現行の `calculateWalk` + `reachableLines` の
   結果と一致する（5分・10分の両方）
2. おのだサンパークへの到達距離が現行と一致する
3. 5分の徒歩圏が10分の徒歩圏に含まれる

加えて、折り返し分割の単体検証を追加する。

4. 環状路を持つ小さな合成グラフで、山型の頂点が分割され、
   分割後の線形補間が真値と一致する（4.3節の数式による）
5. スナップ点が区間の内部にある場合、そこでも分割される

既存テストの合成グラフ検証（クリッピング、交差の非接続、
歩行者一方通行、到達不能判定）はそのまま維持する。

## 7. スコープ外

- **施設データの拡充** — `shopping.geojson` は19件のままとする。
  クライアント判定にしたことで、焼き込みとは独立に追加できる
- **バス停データの網羅性** — 現行の `bus_stop.geojson` 1,085件で進める。
  緯度の上限が 34.4269 であり、萩市北部・須佐・田万川あたりが
  含まれていない可能性があるが、網羅性の改善は別途おこなう
- **面（ポリゴン）の生成** — 到達可能な道路を線で描く現行の表現を維持する
- **配信のタイル化** — 1停留所1ファイルで進める。
  近傍停留所をまとめる案は、必要になってから検討する

## 8. 既知の天井

- **バジェットが666.7m固定** — 「時速4km × 10分」ちょうどで焼く。
  後から15分バンドや時速5kmを追加すると**全件の焼き直しが必要**になる。
  余裕を持たせるとセグメント数が二乗で増えるため、今は詰めて焼く。
  `ponytail:` コメントで天井と再焼成の手順を残す
- **OSM更新への追随** — 道路データが更新されたら1,085件を焼き直す。
  一度きりの処理として設計し、CIでの自動化は別途検討する
- **任意地点からの計算ができなくなる** — 現行はバス停以外の任意座標でも
  計算できるが、焼き込み後はバス停に固定される。
  本アプリの用途（バス停ごとの徒歩圏）では問題にならない
