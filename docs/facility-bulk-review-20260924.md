## Jevの実測と効率評価

| 試行 | Jevへの入力 | 処理結果 | 評価時間 |
|---|---:|---|---:|
| 施設の調査経路（7,764件・32群） | 8,747 input / 2,081 output tokens | 32群を一次資料一括、公式名簿、公式確認前提のGoogle候補調査、延期に振り分け | 133.98ms |
| 近接重複（195組のうち66組） | 10,914 input / 2,651 output tokens | 129組を距離で先に除外。Jev後にGPT候補30組へ | 207.66ms |

ただし施設の経路決定では、生のJevラベルと最終採用ラベルが完全一致したのは32群中7群。残る25群は、ブランド／独立店の分割や公的名簿優先などの機械・人手ルールで経路を細分化した。したがって、効率化の実績は「全施設をJevが処理した」ことではなく、全件を数・距離・ID・住所でコード処理し、Jevを意味判断が要る候補の事前選別へ限定できたことにある。実質的な節約は、重複候補のGPT投入を195組から30組へ減らした部分。これを施設状態の検証や自動更新の実績として数えない。

今後の標準工程は、(1)コードで元ID・住所・カテゴリを正規化し、距離や件数を計算、(2)公式CSV・名簿をコードで一括取得／照合、(3)一致しない名称・施設範囲の判断だけJevへ、(4)調査が必要な不明群だけ通常ChatのGPT-6 Proへ公式原ページ調査を依頼、(5)Codexが公式ページと元IDの対応を独立確認して差分化、(6)ID・座標・形状不変と全体件数を検査する。JevはWebの事実確認器ではなく、数値・日付・件数・構造不変条件を担当させない。

この分担はTypeSafe公式資料とも整合する。entity alignmentの例は、候補生成を先に安価に絞った後、同一・別・人手保留の三択で判断し、誤統合を避けている。confidence routingは誤判定時のリスクで閾値を変えるよう説明し、Jev 1.13の注意点は算術・件数・日付比較をコードで行い、無関係な状態を入力前に絞るよう推奨している：[entity alignment](https://docs.typesafe.ai/cookbooks/entity_alignment)、[confidence-gated routing](https://docs.typesafe.ai/patterns/confidence-routing)、[Jev 1.13の限界と使い分け](https://docs.typesafe.ai/model-jaggedness/jev-1.13)。
