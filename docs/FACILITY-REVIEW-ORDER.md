# 施設更新の処理順 — 次バッチの提案

状態：2026-09-25のユーザー要望を受けた**提案**。新しい大量調査・Jev課金は未開始。既存4施設のPR反映とは区別する。

## 目的

個人店・地域の小規模店の閉店と新規開店を拾う。既存7,764件の点検だけでは未登録の新店を発見できないため、「既存記録の更新」と「新店の追加」を同じ変更候補台帳で扱う。

チェーン店・大型薬局は公式一覧をまとめて確認しやすく、先行する価値がある。ただし、それだけで個人店の調査完了とはしない。運営主体の区分は名称から推測せず、個人・地域店／全国・広域チェーン／未判定を記録する。

## 最初の40候補の処理順案

1. **候補を先に固定する。** 保存済み候補を回収し、地域ニュース、店舗公式告知、確認できる公式Instagram・LINE、Googleマップの変化等から追加する。未登録新店も候補に入れる。検索日時、検索語、取得できたURLと要旨、取得不能の情報源を記録する。
2. **個人・地域店20件、チェーン12件、運営区分未判定8件**を第一バッチの目安とする。これは暫定配分であり、測定済みの最適比率ではない。どこかの枠が不足したら、候補の不足数を示し、他の枠へ黙って振り替えない。
3. **市町を一巡する。** 自治体名を正規化して昇順に固定し、各市町から1候補ずつ選ぶ。次の一巡も同じ順。同じ市・同じ大手企業だけで枠を埋めない。市町未判定は別列で残し、調査済みに数えない。
4. **市町内は実施済みの閉店と新規開店を交互に取る。** 初回は閉店、次は開店。片方が空なら他方を取る。その後に移転・改称等、最後に将来の予定情報。同じ種類内はイベント日の新しい順、日付不明は末尾。同順位は初回検出日時、最後に候補キーの昇順で固定する。
5. **照合して採否を決める。** 名称・住所・電話・運営者・座標等で既存ID候補を出す。曖昧な分類にJevを使う場合も、一次根拠や同一性の不足をモデルの自信で埋めない。別店舗を旧IDへ改称しない。一次根拠が揃った閉店・新店・変更をPRへ反映する。

「40件」は候補処理数であって40施設の更新保証ではない。ニュースだけで閉店が確定しない、同じ住所で別サービスが始まる、当日売切れの閉店告知などを含め、採用・保留・誤検知を分けて残す。

## 再現性のために保存するもの

- バッチID、対象市町、対象期間、情報源一覧、検索語・日時・取得結果。
- 原記事URL、取得日、本文または許容範囲の要旨、発生日、一次／二次情報、対象店舗範囲。
- 候補キー、運営区分と根拠、元ID候補、採否、保留理由、次に必要な資料。
- 入力スナップショットのSHA-256、並べ替え規則の版、確定した処理順のCSV。
- Jevを使った行だけ、送信入力、生応答、モデル、時間、使用量、判断への採用有無。
- 実際の追加・閉店除外・名称等変更の件数とGitHubコミット、CI結果。

再現対象は「同じ保存済み入力から同じ処理順と採否検査を得る」こと。検索エンジンの将来の結果や変化するSNS画面が同じになるとは保証しない。検索は再実行して上書きせず、新しい時点の入力として差分を残す。
